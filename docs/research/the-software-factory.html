The software factory, assessed against this repository

Dex Horthy's factory writing — twelve-factor agents, context engineering, the dark-factory failure and SlopCodeBench — set beside a repository that already runs most of it. What applies, what does not, and the three things the framework names that are not named here.

Question · What is the software-factory approach, which of it applies here, and what should change as a result?

The verdict

This repository is already a light factory, and it got there from the other direction. Horthy arrives at his conclusions by managing agents and watching a codebase rot; this project arrived at nearly the same practices by chasing determinism.

The two roads meet at one rule, which Horthy calls back pressure: you may hand a loop only as much autonomy as you can cheaply and reliably verify. A rolling state hash, a committed golden trace, a poison suite and a six-row determinism matrix are not agent-management tools by intent — but they are the best back-pressure instrument in this repository, and they already exist. So the useful output of this note is not “adopt the factory”. It is the three things the framework names that this repository has not named.

§0The three gaps, in order of what they cost

  1. The autonomy gradient is felt, not written. The simulation is verified six ways from a shell; the client is verified by a person dragging a slider once. Back pressure says those two halves must not receive the same amount of agent autonomy. Nothing in AGENTS.md says so.
  2. -Regenerate is a self-certifying escape hatch. Any change to the rules can be made to pass the gate by rewriting the artefacts the gate checks against. This is correct by design, and there is no guard on it.
  3. The slop surface here is prose, not code — and nothing checks prose. Horthy's degradation curve applies to specifications, and his framework assumes the spec is the stable thing. Here the spec is the thing that moves: seven vision reversals in five days.

And one structural mismatch. The factory's core promise is throughput, and this project does not want throughput. The README says the game is built “for the pleasure of building it”. Horthy's numbers — 35,000 lines in seven hours, $12,000 a month in tokens for three people — answer a question nobody here is asking. Take the verification discipline; leave the volume.

§1What the approach actually is

Horthy's position is not one document. It is four artefacts written over about eighteen months, and they only make sense read in order, because the later ones retract the optimism of the earlier ones.

1.1Twelve-factor agents — agents are mostly ordinary software

A reaction against framework-shaped agent loops. The thesis: reliable LLM software is deterministic code with model calls placed at chosen points, not a loop handed a goal. The load-bearing factors for coding work are own your context window, own your control flow, small focused agents, and make the agent a stateless reducer so it can be paused and resumed.

1.2Context engineering — research, plan, implement

The practical workflow, organised around frequent intentional compaction: because a model is a stateless function, context quality is the only lever, so you deliberately distil progress into markdown artefacts and start fresh rather than letting a window fill with tool output. Three phases, each producing a reviewable artefact — research establishes which files matter and how information flows; the plan names exact files, exact changes and the verification for each; implementation runs phase by phase, compacting between them.

The load-bearing claim is about where human attention goes. A wrong line of code costs seconds. A wrong line of a plan costs hours. A wrong line of research costs days, because everything downstream inherits it. So review moves upstream: humans read the 200–300 line research note and the plan, and read the resulting diff much more lightly. It also names a metric that is not correctness — mental alignment, the degree to which humans still recognise their own codebase.

Rules of thumb that travel with it. Target 40–60% context utilisation; roughly 170k tokens are usable before quality degrades. Prioritise correctness, then completeness, then brevity — wrong context is worse than verbose context. Delegate search to subagents so grep output burns a window nobody keeps. Throw out research that contradicts expectations rather than force-fitting it. Do not skip research. And there are no magic prompts — the result comes from the process.

1.3The dark factory, and its failure

From July to November 2025 Horthy ran a fully automated factory: agents wrote, reviewed and deployed, and no human read a line. It failed — and the interesting part is how. The tests stayed green the whole time. What accumulated was comprehension debt: the gap between the volume of code and anybody's understanding of it. It surfaced when a single bug took weeks to find.

The diagnosis is a training-signal argument, and it is why he thinks better harnesses cannot fix it: reinforcement learning rewards passing tests, not preserving design. Whether an architecture held up is observable in months or years, which is too long a horizon to propagate as a reward. Models are, by construction, optimised for the thing that is cheap to check and indifferent to the thing that is not.

1.4Harness engineering is not enough — the factory as a loop

The factory is a closed loop: intent and production signals feed a queue; the harness builds; automated checks and review gate it; deploy ships it; monitoring turns production back into signals. Harness engineering — orchestration, sandboxing, tools — makes the build box faster and cannot make the gate box smarter. What falls out of that framing:

  • Back pressure. Autonomy is capped by cheap, reliable verification. Verification, not generation, is the constraint on the whole system.
  • Graph workflows, not open loops. Mostly deterministic code with LLM steps sprinkled in at the right points. Agents hold coherence for roughly three to ten steps and lose the thread past twenty.
  • Small verifiable automation beats large autonomous automation. His example is a nightly cron that fixes exactly one anti-pattern and opens one small pull request.
  • The codebase is part of the harness. Strong typing, test seams, short call stacks, clear boundaries. Code that is cheap to verify is code an agent may be trusted with.

1.5SlopCodeBench — the evidence

The newest artefact measures the thing the argument depends on. Requirements are revealed incrementally across 17 checkpoints, so the test is long-horizon maintenance rather than one-shot correctness, and it scores strict pass alongside 41 slop metrics — volume, cyclomatic complexity, duplication, single-use functions, dependency-graph propagation cost.

Model Strict pass Output shape
Opus 5 24% (4 of 17) ~5× more functions; 51% of output is test code
Opus 4.8 6% 11–24% test code
Sonnet 5 6% 11–24% test code

Complexity, duplication and violations climb across checkpoints for every model tested. The conclusion worth carrying here: models degrade codebase quality over time, and no amount of process removes the need for a human gate until that number is far higher than it is.

Two places this repository is ahead of the framework, and they should not be quietly re-recommended. Golden screenshots were tried and rejected with evidence — capture-match-frames.ps1 records that two frames whose bones were definitively swapped rendered pixel-identical, reproducibly, so the obvious “hash the frame at the landmark tick” gate is already known here to be a gate that cannot fail. And the gate's tree-clean step states back pressure more precisely than Horthy does: a step that repairs what it finds “would have gone green through every regression it exists to catch”.

One number worth putting beside SlopCodeBench: sim/ is 7,106 lines against 5,420 lines of tests — a ratio of 0.76, on a simulation whose every rule is checked against a committed trace. This is not a codebase where an agent can quietly degrade correctness.

§3Where it does not fit

3.1Throughput is not the goal

The factory exists to convert intent into shipped code faster, and its published evidence is volume. This project's README says it is built for the pleasure of building it, the art budget was deliberately $0, and the build order was re-sequenced by what is cheapest to learn rather than by what unblocks what. Adopting the throughput apparatus would optimise a quantity the project does not value, and the first casualty would be the ADR-and-vision discipline that is currently its best asset.

3.2Mental alignment means something different with one human

Horthy's alignment metric is about a team drifting apart from a codebase. Here there is one person. The disease is the same but the epidemiology is not: the risk is not that colleagues cannot read the code, it is that Sam in November cannot read what agents wrote in August. The mitigations already in place are stronger than most teams manage. This part of the framework is discharged and needs no new machinery.

3.3The client half cannot be given the factory's verification

The factory assumes the gate can be made cheap. Half of this repository is a Unity project where it cannot: engine tests need a licence and a multi-gigabyte image, the editor holds an exclusive project lock, and the one artefact that would make visual regressions checkable has been measured here to be insensitive to a definitively broken skeleton. This is not a gap to close. It is a permanent asymmetry, and the right response is to make it explicit rather than to keep trying to close it.

3.4The framework assumes the specification is the stable thing

This is the sharpest misfit, and it runs the other way from every other item here. The review inversion — read the plan hard, read the diff lightly — rests on the plan being the cheap thing to be wrong about. This repository has leaned into that further than Horthy does: a seven-step build order with zero lines of code written against any of it, and a planning apparatus that produces decisions rather than deliverables by default.

But the plan here is not stable. In the five days to 7 August: six vision reversals landed, then a seventh; map #70 was rescoped mid-flight when two of its four questions turned out to rest on dead premises; and the economy obligation for step 1 has now read three different ways. The map says the churn is the point — being wrong on paper costs a text file — and that is a fair defence of each individual reversal.

The aggregate is what needs the gate, and there is no gate on prose. Nothing fails when two documents disagree. Two measured examples, both from the same file:

What docs/README.md said What was true Drift
The Element TD correction is “not yet applied” Applied 3 Aug at 14:05 by PR #61 3½ days
“No mazing, ever”, and the one-hex corridor The maze reversal had landed the day before 1 day

Neither is a large defect. Both are exactly the shape SlopCodeBench measures in code — a claim true at checkpoint N and quietly false at N+1 — and every frontier model in that benchmark exhibits it. There is no SlopCodeBench for design documents, and this repository's dominant output is design documents.

The 7 August consolidation is the right response and it already happened. It archived the deep dives, moved reversal churn into a decision log, and demoted the index — and its own log entry names the cause precisely: “the exact failure mode of keeping the same fact in two files”. That is a better diagnosis than anything in the factory literature, which does not discuss spec rot at all. What it does not do is make the next occurrence cheaper to find: both defects above were caught by a human re-reading days later, which is the manual regime this project has already rejected for the simulation.

§4Recommendations

Ranked by the cost of not doing them. These are proposals, not applied changes.

4.1Write down the autonomy gradient Half an hour

Back pressure is currently intuition. Make it a rule in AGENTS.md, per area: what verifies this, and therefore how much an agent may do unattended.

AreaWhat verifies itAutonomy
sim/, tests, poison Gate, matrix, IL scan, golden trace Full — a green gate is sufficient
content/*.txt The trace moves and must be regenerated deliberately Full to change; never to regenerate
simcli/, tools/ The gate exercises the entry points Full
docs/ Nothing Full to draft; the human review is the gate
client/ non-visual Playmode and editmode runners, off CI Agent writes; a human runs the runner
client/ visual sit-down.md and a person Agent proposes; the human decides
Art assets Nothing automatable Human only — already the standing rule

AGENTS.md is 71 lines and just went on a diet specifically so instructions could live there and measurements could not. A seven-row table is an instruction.

4.2Put a tripwire on -Regenerate Highest risk

The script guards the ways it can be misused — it refuses to run alongside -Verify, and refuses to run against anything but the committed simulation. It does not, and cannot, guard the thing that matters: a change to the rules plus a regeneration is a green gate, on all six matrix rows. This is correct design — the alternative is a gate that can never go red on a deliberate content change — and it is precisely the hole the dark factory fell through, because there too the tests stayed green.

The fix is not technical, it is an attention gate: a diff touching the golden trace, the landmark table or content/golden/ is a diff a human reads, always. A CODEOWNERS entry, or a gate step that fails a pull request touching those paths without a regenerated-deliberately label. Make the escape hatch loud rather than closing it.

4.3Bind map #70 to a built step, not a decided one Scheduling consequence

The coherence range — three to ten steps, lost past twenty — is about agent loops, but the planning loop here has the same shape and is on its second rescope. Change the stop condition from “nothing left to decide” to “step 1 is built and the gate is green”, and do not open the seam-9 board map until then. Steps 1 to 4 need no engine, no licence and no editor; nothing stands between the decisions already made and a shell.

This is also the only real answer to §3.4. Implementation is the back pressure on specification. Nothing else is.

4.4Adopt the nightly one-anti-pattern cron — pointed at the documents Most transplantable

Aim Horthy's most portable single practice at this repository's actual slop surface. A scheduled agent that checks one documentary invariant and opens one small pull request:

  • every issue or PR number cited in docs/ still says what the document claims — an issue called open that is closed, a correction called “not yet applied” that merged;
  • every warning flag in docs/ has an open issue, and every closed issue's flag is cleared;
  • every ADR is referenced by the code it governs, and every ADR number cited in code exists;
  • every tick quoted in sit-down.md matches content/landmarks.txt;
  • every overturned claim in an archived deep dive is marked as such in the vision's §9 and the document's own banner.

The first check alone would have caught both defects in §3.4, on the nights of 3 and 6 August rather than by hand on the 7th. It is also trivially cheap: the numbers are already hyperlinked, and gh issue view --json state is the whole oracle.

4.5Recognise step 4 as the largest back-pressure investment in the plan Reframing

The sweep harness — every unit against every defense, win rate and cost-efficiency to a CSV — is filed as “small, it is text rows”. Under the back-pressure rule it is much more: it is the instrument that makes balance cheaply verifiable, and balance is the most subjective quantity in the game.

Until it exists, steps 1 and 3 add design levers with no gate at all — an agent that changes a cost or adds a roster row produces a green build and an unknown game. That argues for building the harness alongside step 1; or, if the ordering holds, for saying in the vision that steps 1 and 3 are human-judgement steps with no automated gate, which is currently true and unstated.

4.6Keep code review mandatory on sim/, and say why One line

The temptation this repository creates is the exact one that sank the dark factory: the gate is so good that reading the diff feels redundant. It is not, for a reason specific to this design — the gate checks consistency between the rules and the artefacts, not that the rules are the intended rules. A change that moves the trace and regenerates it is invisible to every automated check in the repository, on all six platforms. Make /code-review non-optional for sim/ and content/, on the record, next to 4.2.

§5What to reject

Not thisBecause
Dark mode Agents merging unread SlopCodeBench puts frontier models at 6–24% strict pass on long-horizon maintenance, with complexity climbing across checkpoints for all of them
Reject Eliminating the pull request That is a bet on a live collaborative IDE. This repository's working agreements are built on the opposite property — that nothing depends on a session — and its PRs carry the reasoning the ADRs are later distilled from
Reject Throughput and cost metrics Lines per hour, PRs per day and monthly token spend measure something this project does not want more of
Reject Editor-bridge orchestration Unity's first-party bridge needs a subscription, and working agreement 3 rules out session dependencies regardless. Batchmode is the correct path and already is the path
Reject Golden-frame comparison Already measured here to be insensitive to a broken skeleton. Semantic assertions plus the sit-down are the right instruments; the frames stay documentation
