# The defense the skeleton's one match is fought by, and the wall the OPPONENTS
# open with everywhere else.
#
# THIS IS NOT WHAT A RUN STANDS BEHIND. A run opens on an empty board and stands
# whatever its own build phases put on the map -- see content/commands.txt. This
# file is the wall on the other side: the one the authored match's wave is sent
# at, and the one every member of the canned field pool starts its run behind.
#
# IN THE AUTHORED MATCH THESE SIX NEVER CHANGE. There is no build phase, no
# economy and nothing a mouse does that reaches a match: the defense is this
# file, read once, and from then on it is one array that is never written to.
# Every hit and every death in that match belongs to the creeps.
#
# IN THE CANNED FIELD IT IS A SEED AND NOT THE WALL. A member of that pool is
# recorded once per round, and it builds between rounds the way a run does: it
# opens holding the ruleset's starting purse, spends the same half of it a run's
# scripted player spends, and is paid the same interest and the same flat base
# afterwards. That is the income LINE a run is paid and not the whole of what a
# run has: a run also banks its unspent offensive share and is paid a bonus, and
# a stand-in gets neither. What the wall declines to spend out of its half is
# what carries into the next round; the other half is the wave's, and the wave is
# the authored column in content/field.txt. Every round builds before it is
# recorded, the first one included, so round one stands these six plus whatever
# round one's own share bought and round ten stands ten rounds of that income on
# top of them. On this content round one buys nothing -- an opening share of 50
# gold against a cheapest upgrade of 92 -- but that is a fact about this file and
# not a rule.
# The wall a growing wave is measured against therefore grows too, which is the
# whole reason a late round of content/sweep.csv is worth reading. These six
# stand beside that opening purse rather than out of it -- a member is a
# RECORDED round and not a run played from nothing, and 344 gold of towers
# could not be bought out of an opening hundred anyway.
#
# WHAT IT GROWS INTO, ON THIS BOARD, IS SIX MAGES BY ROUND SIX. The route below
# is covered end to end already, so the rule finds nothing to place and spends
# on upgrading instead: the four archers become mages one at a time in rounds
# two, three, five and six -- 344 gold of wall, then 396, 448, 448, 500 and 552
# from there on -- and after that every placement is the dearest row the roster
# has and there is nothing left to buy. IT IS A DEARER WALL AND A WORSE ONE. A
# mage costs 92 against an archer's 40 and fires once every 54 ticks against 18
# -- a third less damage a tick for more than twice the price -- so the
# committed run gets MORE past this wall from round two on than it does past the
# seed. "Upgrade the oldest placement into the dearest row" is not "buy the
# better tower", and this is where that shows.
#
# Same rules as units.txt: integers only, no decimal point, comments free.
#
# THE CELL IS A COLUMN AND A ROW, counted the way map.txt is written -- so a
# tower can be placed by counting characters in that file. The simulation
# converts the pair to axial (q, r) on load through the one canonical odd-r
# conversion it owns, which is also what the record format stores.
#
# TOWERS ASCEND BY ROW AND THEN BY COLUMN, AND THAT ORDER IS ASSERTED RATHER
# THAN SORTED ON LOAD. Sorting would leave two identical defenses with two
# different sets of bytes and content-addressing one would stop meaning
# anything. It is also the order the match iterates towers in, and iteration
# order is a simulation input here: where two towers cover the same stretch of
# corridor, both can commit to the same creep on the same tick, and which of
# them lands the killing shot is decided by which one this file lists first.
#
# RANGES OVERLAP ON PURPOSE. A defense whose towers each had the corridor to
# themselves would never exercise overkill, never exercise a shot arriving at
# something already dying, and never make iteration order matter -- so every
# one of these six shares a stretch of corridor with at least one other, and
# the build gate asserts that rather than leaving it to this comment.
#
# THESE SIX WERE COMPUTED AND NOT CHOSEN. They are what CoverThenUpgradeBot's
# rule picks on the current map -- the type covering the most unshot route per
# gold, six times, under the overlap the gate asserts -- because coordinates
# chosen by hand are coordinates that go stale the next time the board is
# redrawn, silently and everywhere at once. The mix is the one this file has
# always had: four bolts and two mortars. The pool goes on applying that same
# rule round after round, so the seed and the growth are one player's judgement
# rather than a hand-placed opening followed by a bot's second opinion.
#
# THE ROUTE IS COVERED END TO END, which the folded board is the reason for: on
# the old corridor six towers left gaps near the entrance and either side of the
# first corner, and a third of the wave walked through them. Here nothing is
# unwatched, so what leaks now leaks because the wall cannot kill fast enough
# rather than because it cannot see. It is also what caps the ghost at six
# towers: a rule that only places where something is unshot at has nowhere left
# to place, however much gold it is holding.
#
# The loader refuses a tower that is off the grid, a tower standing inside the
# corridor, and a tower whose range cannot reach the route at all. The last is
# what a mistyped coordinate looks like, and without the check it would present
# as a balance problem rather than as a fault.
#

#

#          puts nothing at all in the snapshot

#          that flies for eleven ticks and can be orphaned mid-flight
